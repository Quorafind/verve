# P66 JIT 覆盖扩展

**依赖**：P60、P63（在 `electron` 里测量）；调用帧部分与 P65 错开合并  **规模**：L  **修改**：`boa/core/engine/src/vm/jit/`、`vm/call_frame/`、`vm/opcode/call/`、
`vm/mod.rs` 中与调用和进出 JIT 相关的部分、`docs/jit.md`、`boa/SU.md`、对应测试

## 目标

基线里 JIT 几乎没有收益：`fib` 1.24×，`alloc`/`typed` 约 1.05×，其余 1.00×；`docs/jit.md` 记录的 3–12× 只出现在属性/元素访问的微循环里。
本包先**解释为什么**，再按剖析做 `docs/jit.md`「Phase 2, left over」里收益最大的几项，让 JIT 对 P60 套件里的循环型负载
（`fib`、`oo`、`typed`、`alloc`、`vdom`、`closure`）有实在的倍数。

**参考目标**（第 1 步的分析出来后由实现者提出、总控确认）：上述各项 JIT / 解释器 ≥ 2×，其中 `typed` ≥ 5×（P65 合并后的解释器为基准）。

- [`perf-baseline.md`](../perf-baseline.md) 第 3 节：`VERVE_JIT_THRESHOLD=0` 也没改变 `fib`/`oo`/`typed`（298 / 1186 / 3180 ms）。
- P60 的剖析配方；P65 的「状态」（解释器侧改了什么，JIT 的慢路径随之变快）。

### 2. 按分析结果做（候选，顺序以第 1 步为准）

- **类型化数组元素内联**：`GetPropertyByValue`/`SetPropertyByValue` 遇到类型化数组与 `int32` 索引时在机器码里读写（检查同解释器快路径：未分离、在界内、元素类型）。

- **`new` 与对象字面量**：构造调用与 `this.x = …` 的形状转换在编译代码里的路径。
- **字符串与原生调用**：字符串 `+`、`length` 与下标；调用原生函数的固定成本（左项第 4 条）。
- **可盈利性与分层阈值**：如果分析显示热函数因可盈利性规则或阈值没被编译，调整规则并给出依据。

#### 为什么 JIT 几乎等于解释器（前三条原因，证据）

1. **贵的指令还是解释器的处理函数（测量）。** `typed`：`f64.length` 347 ns（稠密数组的 `arr.length` 12.5 ns），类型化数组元素读 60.6 ns（稠密数组 17.2 ns），
   其余 18 条内联指令合计约 25 ns；这三类步进占一轮约 95%。处理函数周期占比：`length` 61%、读 12%、写 11%。辅助对类型化数组每次都回答「慢」，所以多付一次辅助的拒绝。
   同样的形状：`alloc`（十个步进指令里八个是分配、属性定义、字符串拼接、原生调用，359–621 周期）、`oo`（`New` 3,742 周期、`this.x = x` 1,090，对比 `Call` 259、`Return` 136）、
   `vdom`（`GetIterator` 3,161 周期、`IteratorNext` 1,241；`for-of` 每元素 369 ns，按下标 26 ns）。
   反证：和 `typed` 同体的稠密数组循环编译后快 4.0×（48.7 对 196.2 ns），JIT 在辅助适用的地方是有效的。
2. **调用成本与有没有 JIT 无关（测量）。** 一次 JS 调用编译后约 90 ns、解释 105 ns（`zero()` 90.0 / 109.1，扣掉循环本身 1.7 / 14.7）。`fib` 每次调用是 `Call`
   处理函数 180 周期（压帧）加 `Return` 101 周期（弹帧）加 10 次快速辅助调用加 `prepare` 的热度检查 33 周期；扣去探针开销后两个处理函数至少 150 与 75 周期，**超过一次调用的一半**。
   `fib` 每次调用 107 ns（JIT）对 133 ns（解释）就是那 1.25×。`oo` 每轮三次调用、`closure` 的 4.5M 次回调、`vdom` 的递归都付同样的钱。
3. **时间大头不是分派也不是属性访问（测量；`closure` 的占比是推断）。** `new` 空函数 262 ns，带一次 `this.x = x` 579 ns，也就是在新对象上定义第一个属性约 318 ns、
   第二个约 257 ns（形状转换，两层都不缓存）；`{}` 90 ns，字面量每个属性 115–135 ns；`map` 每元素 228 ns；带洞数组 `a[i] = i` 210 ns；空 `class` 的 `new` 610 ns。
   `closure` 约三分之一是初始化循环（210 ns × 1M），三分之二是原生回调。这些 JIT 不去处理就不会变快。

不是原因（测量）：分层阈值与可盈利性规则（全部编译、阈值 0 无变化）、OSR（`typed`、`alloc`、`closure` 都进入了热循环）、编译时间（4–8 ms，`vdom` 21 ms 且只在暖机里）、嵌套调用（`fib`、`oo`、`closure` 都嵌套执行）。

#### 提议的目标

草案目标是 JIT/解释器 ≥ 2×（六项），`typed` ≥ 5×（P65 合并后的解释器为基准）。把比值写成「对同一构建的解释器」会和「共用调用机制」打架：
瘦身 `CallFrame` 同时让解释器变快，比值变不动。所以下面**同时给绝对值（JIT 列，ms）与对今天解释器的倍数**，总控在 P65 合并后用新解释器重算比值。

| 测试 | 现 JIT / 解释器 | 提议目标（JIT 列） | 对今天解释器 | 依据与说明 |
|---|---|---|---|---|
| `typed` | 3265 / 3426 | **≤ 450 ms** | ≈ 7.6× | `length` 与元素内联后每轮约等于稠密数组循环（48.7 + 12.5 ≈ 61 ns，六百万轮 ≈ 0.4 s）。**对 P65 后的解释器 ≥ 5× 达不到**：稠密数组的同体循环，今天解释器 245 ns 对 JIT 61 ns 就只有 4.0×，即使 P65 让类型化数组的解释器路径追平数组，JIT 的上限也是 ≈ 4×。改为 **≥ 3.5×（对 P65 后的解释器）且 ≤ 450 ms** |
| `fib` | 288 / 358 | **≤ 180 ms** | ≈ 2.0× | 每次调用 107 ns → 约 65 ns：压帧弹帧 ≥ 60 ns 要砍掉大半，需要编译代码对普通函数的直接调用（共用调用机制）。仅靠砍辅助调用（≈ 20 ns）只能到 ≈ 235 ms。若瘦身 `CallFrame` 让解释器也快 20%，对新解释器的比值约 1.6–1.7× |
| `oo` | 1264 / 1275 | **≤ 600 ms** | ≈ 2.1× | 每轮 ≈ 1260 ns = 三次调用 ≈ 270 + `new`（≈ 580 对一次 `this.x =`）+ 其余。`new` 与第一次属性定义若降到 ≈ 200 ns（缓存形状转换、构造调用不走通用路径），每轮 ≈ 600–650 ns。**对 P65 后的解释器大概只有 1.5–1.8×（推断）**：P65 动的是同一批处理函数 |
| `alloc` | 302 / 334 | **≤ 220 ms** | ≈ 1.5× | 每轮 ≈ 970 ns：`{i, s, n:{v}}` 671 + 拼接 112 + `push` 89 + GC。对象分配本身（`{}` 90 ns）与字符串、`push` 原生是 JIT 够不着的下限，约 380 ns；**2× 达不到**（上限 ≈ 1.8×，推断），除非 P64/P65 先降分配 |
| `vdom` | 71 / 81 | **≤ 55 ms** | ≈ 1.5× | 迭代器协议（`GetIterator` + `IteratorNext` + …）约占 JIT 运行的三分之一（处理函数周期，含探针开销）；数组 `for-of` 内联后约快 1.35×，叠在现有 1.14× 上 ≈ 1.5×。其余是字符串拼接、对象字面量、`Map` 原生（P64/P65）。**2× 达不到** |
| `closure` | 624 / 646 | **≤ 430 ms** | ≈ 1.5× | 初始化循环（带洞数组按下标写，210 ns × 1M）内联后省约 190 ms；剩下约 410 ms 是 `map`/`filter`/`reduce` 的原生到 JS 回调（≈ 185 ns/元素，两百二十五万次），那是原生调用 JS 的路径，**JIT 不能降**，属 P65（内建调用方式）与调用机制。**2× 达不到**（需回调降到 ≈ 50 ns） |

#### 提议的顺序与预期收益（第 2 步候选）

按（收益 ÷ 风险）排，标出是否动共用调用机制：

1. **类型化数组 `length` 与元素内联**（`GetLengthProperty`、`GetPropertyByValue`、`SetPropertyByValue`）。`typed` 3265 → ≈ 450 ms；其他测试不受影响。
   **不动调用机制**。依赖 P65 对类型化数组内部表示与 `length` 路径的改动，所以**在 P65 合并之后做**（布局检查要跟着新结构）；`length` 的内联要保证
   `%TypedArray%.prototype.length` 未被改写、实例无自有 `length`。
2. **数组 `for-of` 内联**（`GetIterator`/`IteratorNext`/`IteratorDone`/`IteratorValue`/`IteratorReturn` 在迭代器未被改写时的整段）。**候选清单里没有，建议加上**：
   每元素 369 ns → ≈ 30 ns；`vdom` ≈ −25%，应用代码里到处都是。**不动调用机制**。
3. **越界追加写**（`a[i] = x`，`i == length` 或带洞数组，`SetPropertyByValue` 的辅助现在拒绝）：`closure` −190 ms，`idx_append` 168 → ≈ 30 ns。**不动调用机制**。
4. **`new` 与对象字面量**（`StoreEmptyObject` + `DefineOwnPropertyByName` 的形状转换缓存、`this.x = …` 的转换、`This` 与构造器 `CheckReturn` 内联）。
   `oo` ≈ −45%，`alloc` ≈ −30%，`vdom` 一部分。**`New` 在 `vm/opcode/new/` 与 `builtins/function/`（`function_construct`），不在本包任务书列的目录里**；
   与 P65 的「首属性定义 ≈ 319 ns」同一处，**P65 合并后再测**，P65 修掉多少就少做多少。
5. **调用本身**（瘦 `CallFrame`、编译代码对普通函数的直接调用、`this`/函数不进值栈）。`fib` 288 → ≈ 180，`oo` 每轮再省约 90 ns，`closure`/`vdom`/一切带调用的代码都受益。
   **动共用调用机制：`vm/call_frame/`、`vm/opcode/call/`、`vm/mod.rs` 的 `push_frame`/`handle_return`，必须在 P65 之后合并，并且要保证 P65 不被它弄坏**
   （P65 的任务书声明不改这些；它的内建调用方式变动要在合并前跑 P65 的差分与性能数字）。收益最大也风险最大，所以放在 1–4 之后，用前面几项的数字定它的预期。
6. 字符串与原生调用（`+`、`length`、下标已有一部分内联：`strlen` 11.4 ns，`strindex` 52 ns；原生调用固定成本 `Math.abs` 78 ns）：收益小，排最后。
7. 可盈利性与分层阈值：**不用动**，数据显示没有热函数因它们被漏编。

另外发现两点，不在候选清单里，记在这里：`Div` 没有内联（步进 11.8 ns，对内联 `Add` 3.3 ns），数值循环里除法会拖慢，成本低、收益小，可顺手做；
空 `class` 的 `new` 是 610 ns，比空函数的 262 ns 慢一倍多，原因没有深挖（推断是类构造器的字段/环境初始化），属项目 4。

#### 没能测量的

- **没有采样剖析器**（禁止弹窗、提权、浏览器），所以没有 `perf-js.md` 里那种「前 10 个自耗时函数」表；用进程内计数与周期计时代替，周期含探针开销，已逐处注明。
- **没有逐指令的编译后耗时**：内联指令在机器码里，无法单独计时；内联部分的耗时是用差分微探针（同循环不同循环体）减出来的，不是直接计时。
