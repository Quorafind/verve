# P67 `verve run` 默认开代码缓存

**依赖**：P62  **规模**：M  **修改**：`src/code_cache.rs`、`src/code_cache_load.rs`（P62 新建）、`src/code_cache_pack.rs`（新建，见「状态」）、
`src/code_cache_mark.rs` 与 `src/code_cache_sweep.rs`（新建，见「状态」：前者装「见过」标记的读写与上限，后者装第 3 节的淘汰，
`src/code_cache.rs` 已在 `ci/style/large-files.txt` 的 1666 行额度内放不下这两件事）、
`src/cli.rs`、`src/lib.rs`（只限缓存的公开 API 与 `CodeCacheStats`）、`tests/code_cache.rs`、`tests/common/mod.rs`（只限测试的隔离）、
为默认开而必须改测试夹具时 `tests/embedder_hooks.rs`、`tests/jit.rs`、`tests/proxy.rs`、`tests/rebon.rs`、`tests/run_as_node.rs`（只限注入临时环境），
`scripts/js-bench/run.sh`（固定缓存设置）、`docs/startup.md`；为降低首次运行成本而必须改 Boa 时，`boa/core/engine/src/code_cache.rs` 与 `boa/SU.md`

## 目标

代码缓存现在要加 `--code-cache=<dir>` 或 `VERVE_CODE_CACHE` 才开。暖缓存把 Rebon 的组合从 167 ms 降到 105 ms，
把 `require('typescript')` 从 1,089 ms 降到 169 ms（P62）——用户不知道这个开关就拿不到。本包让 `verve run` **默认开**，
并先解决默认开以后才暴露的三个问题：

1. **首次运行变慢**：`docs/startup.md` 实测冷缓存 212 ms，比不开缓存（167 ms）慢约 27%。只跑一次的脚本反而吃亏。
2. **旧缓存没人删**：每个构建一个 pack（上限 64 MB），"old ones are left for the embedder to delete"。默认开以后 CLI 就是这个调用方；
   开发时频繁重编译，几天就能堆出几 GB。
3. **多个进程同时写**：pack 是"临时文件改名"，写入前会合并磁盘上已有的条目，但两个进程的合并与改名之间有竞争窗口。
   原属 P42 第 1 节的并发 flush 修复与测试移到本包，P42 直接使用。

只改 CLI 的默认值：嵌入方的 `Runtime::new()` 仍然默认关（由嵌入方自己决定目录与密钥）；Electron 的接入仍归 P42。

## 接口契约

### 1. 默认目录与开关

- 默认目录：Windows `%LOCALAPPDATA%\Verve\code-cache\`；其他平台 `$XDG_CACHE_HOME/verve/code-cache/`，未设时 `~/.cache/verve/code-cache/`。
  与密钥目录（`%LOCALAPPDATA%\Verve\code-cache-secret`、`~/.config/verve/…`）分开，信任模型不变：密钥不在缓存目录里。
  目录的创建与权限检查照现有 `set_code_cache_dir_with_user_secret`。
- 优先级：`--no-code-cache` > `--code-cache=<dir>` > `VERVE_CODE_CACHE` > 默认目录。`VERVE_CODE_CACHE=0`（以及 `off`、`false`）表示关；
  空值视为未设置（现状）。`USAGE` 与 `cli.rs` 文件头的表格同步更新。
- **默认开绝不能让一次运行失败或多打输出**：默认目录建不了、不可写、权限检查不过、密钥读不了时，静默不用缓存继续运行
  （只在显式给了 `--code-cache`/`VERVE_CODE_CACHE` 时才像现在一样打印一行 `verve: code cache … not used`）。
  只读的家目录、CI 容器、`HOME` 未设置都要覆盖到。
- `-e`/`-p` 的源码本身不进缓存（与现状一致），它 `require`/`import` 的文件照常进。`worker_threads` 与 `child_process` 启动的 `verve` 子进程沿用同一规则。

### 2. 首次运行的成本

先**测清楚冷缓存多出的 45 ms 花在哪**（多编译了 lazy 本来不编译的函数？写盘与 HMAC？进程退出时同步 flush？），写进 `docs/startup.md`，再选方案。候选：

- **第二次才写**（Chrome 的做法）：第一次运行只记下"见过"（例如 pack 索引里只存键、不存代码，或单独的小文件），照 lazy 正常运行；
  第二次运行发现见过才编译全部函数并写入；第三次起读缓存。代价：要两次才变快。
- **把多出的编译与写盘挪出关键路径**：主脚本与事件循环结束后、进程退出前再编译剩余函数并写入；或只写已编译的部分，
  其余函数在以后的运行里首次调用时补写。要说明进程总时间（不只是脚本内时间）怎么变。
- 其他实现者认为更好的方案。

方案选定前写一段比较（各自的冷/二次/暖时间、实现量、对信任模型的影响），总控确认后再实现。

### 3. 旧缓存的淘汰

- 打开 pack 时更新它的修改时间（或在索引头里记最近使用时间），作为"最近使用"的依据。
- 每次运行在**空闲时**（首次 flush 之后，不在启动路径上）检查缓存目录：删除超过 **14 天**未使用的其他构建的 pack；
  目录总大小超过 **512 MB** 时按最近使用从旧到新删除其他构建的 pack，直到低于上限。当前构建的 pack 不删。
  多个已安装的 Verve 版本共用默认目录时，它们各自的 pack 都在用，不会互相清掉。
- 检查本身限频（例如目录里放一个时间戳文件，一天最多查一次），并且失败只是跳过。
- 淘汰函数做成可复用的（P42 用它淘汰 Electron 应用的旧 generation 目录）。

### 4. 并发写

- 临时文件名带进程号与随机后缀，互不覆盖；改名前重新读一次磁盘上的 pack 合并（现状已合并，确认竞争窗口内最多丢失另一个进程**一次**的新增条目，且永不损坏）。
- 测试：4 个进程同时加载不同模块并 flush，重复若干轮，最终 pack 可读、标签全部有效、每个进程的条目在下一轮后都在。
- 在 Windows 上目标文件被另一个进程打开时改名会失败：这时放弃本次写入（下次再写），不报错、不重试阻塞。

#### 结论：冷启动多出的时间不是一个来源

1. **大模块图：多出来的几乎全是「把每个函数都编译一遍」。** 同一 pass 内（表 B，负载 24–42%），`compile` 占缓存开销的
   组合 13.93/28.48（49%）、`typescript` 344.74/430.05（80%）。这正是懒编译本来省掉的那部分：
   `Module::code_cache` 要把整个模块写下来，就必须有每个函数的字节。其余是固定开销加哈希：
   `typescript` 除编译外还有 33.61（源码 SHA-256 求键）+ 32.99（签名），都在 9 MB 源码/代码上。
   进程退出时**没有**同步 flush 的额外负担：`write` 不 `sync_all()`，`process::exiting` 里那次 flush 就是表 B 的 write 段。
2. **小脚本：多出来的全是固定 I/O。** `compile` 只有 0.02 ms，同一 pass 内其余 10.0 ms 是建目录 3.07 + 原子写 4.43 +
   读密钥 1.57 + 指纹 0.47 + `real` 0.43。这也说明**缓存对小脚本在任何一跑都不划算**（暖跑 29.2 对不开缓存 27.9）。
3. **暖缓存也不是白拿的**：`typescript` 暖跑 229 ms 里 17（源码 SHA-256）+ 37（读 17.8 MB 并逐条验签）≈ 54 ms
   是缓存自身开销；组合暖跑 66.3 ms 里约 4.8 ms。这是「第二次之后的税」，本包不动它（P42 的「Faster reading back」那条）。

**推荐 A（第二次才写），并加一条「值得缓存」门槛：一次运行载入的源码总量低于阈值（例如 64 KB）就完全不碰缓存**
——不建目录、不写标记、不读密钥。理由全部来自实测：

- 「第一次 ≤ 105%」这条，`typescript` 的 105% 是 1,215 ms、比现状冷跑（1,538.7）低 320 ms；组合的 105% 是 108.9、
  比现状（122.5）低 14 ms——**只有第一次不做那次 eager 编译才能满足**；写盘、HMAC、建目录全加起来也不够。
- B 不行的真正原因**不是**「语法树被丢掉」：懒编译其实保留了它（`LazyCode.pending` 里是 `Pending::Ast(PendingFunction)`，
  带 `body: FunctionBody`，见 `boa/core/engine/src/vm/code_block.rs:193`、`boa/core/engine/src/bytecompiler/function.rs:42`）。
  B 不行是因为**验收量进程总时间**，编译放在退出前，总数一分不少。
- C 不行是因为读回路径只有 `Pending::Cached`（按索引取记录），补不出没写进去的函数，只能重新解析。

A 的四个细节，都由测量决定：

1. **标记不带 HMAC、也不建密钥。** 第一次跑只建目录并写一个小标记，不读密钥、不写 pack。
   首次在一台机器上建密钥单独测到 16.1–34.9 ms（`sync_all` + 硬链接，负载 70–82%），低负载也有 6.6–10.4 ms；
   若放在第一次跑，「单文件任何一次 ≤ +2 ms」当场就破。伪造标记只多付一次编译，不削弱信任模型。
2. **标记记「哪段源码见过」，但不能在第一次跑就为每份源码算 SHA-256。** `typescript` 那 33.61 ms 的求键若加到
   第一次跑，`typescript` 会到 ≈1,195 ms（仍在 1,215 以内），但组合会到 ≈110 ms、**超出 108.9**。
   所以标记只存已在手的东西：**文件路径 + 大小与修改时间**（各模块载入时本来就知道），第二次再正式算键写条目。
   伪造路径让 Verve 多编译一次，与伪造标记同级。
3. **门槛在「知道载入了多少」之后判定**，所以目录与标记都放到**退出前**写（总量已知，且不在启动路径上）。
   这条同时解决小脚本：`hi.cjs` 只有 402 字节，低于门槛，**任何一跑都不碰缓存**，于是「单文件任何一次不慢于 2 ms」
   是 0 ms 而不是勉强压在线上。没有门槛时我先前算的 ≈29.3 是错的：那个估法漏了 pack 的序列化与写盘，
   而重负载下光建目录就要 2.1–5.5 ms（表 C），+2 ms 守不住。
4. **写条目的那一跑（第二次）把 pack 的固定成本压下来**：pack 不需要每次构造新 DACL，它建在已是「仅本人可达」的
   目录里，普通创建即继承同一份 DACL（现有测试 `ordinary_children_inherit_access_only_for_the_current_user` 正是
   断言这件事）。表 C 同一 pass 内 5.51 → 2.23 ms。

**余量与风险（唯一没有余量的地方）**：组合的第一次只允许 +5.2 ms（103.7 → 108.9），而实测要加的
建目录 1.36–4.09 + 指纹 0.21–0.51 + 小标记 1.30–3.19 合计 **2.9–7.8 ms**：低负载够用，**重负载会超**。
第二阶段的实现按这个顺序收紧，每一档都重测：

1. `check_private` 改成**真正要用缓存时才做**：第一次跑只建目录、只写标记，不做 DACL 校验。
   依据是**推断而非单独计时**：`dir` 这一段是「建目录 + `check_private`」，暖跑里目录已存在、只剩
   `check_private`，读到 0.74–0.90 ms（负载 24–42%），而首次 `dir`（含建目录）在重负载是 6.3–11.3 ms；
   两者相减说明建目录占大头，但 `check_private` 在重负载下的确切值本包没有测，第二阶段要先量它。
2. 标记写成**一个文件、一次 `write_all`**，不按模块逐条追加。
3. 仍不够时，把标记并进第一次 flush（本来就在退出前），不再单独开文件；极端情况下第一次完全不建目录，
   把标记放进用户密钥目录（那里本来就已经存在、同样只有本人可达），代价是「密钥目录」里多一个非密钥文件，
   要在信任模型一节单独说明。

若三档收紧后组合仍守不住 108.9，本包的建议是把验收改成「第一次 ≤ 110%（组合）与 ≤ 105%（其余）」，
并把这条改动单独提给总控——**不隐瞒**：按现有实测，组合这条线在原定的 105% 上没有稳定余量。

#### 第 1 节（默认目录与开关）设计要点

- 目录：Windows `%LOCALAPPDATA%\Verve\code-cache\`；否则 `$XDG_CACHE_HOME/verve/code-cache/`，未设时
  `~/.cache/verve/code-cache/`。密钥目录不变（`%LOCALAPPDATA%\Verve\code-cache-secret`、`~/.config/verve/…`），
  所以「密钥不在缓存目录里」这条继续成立。
- 优先级 `--no-code-cache` > `--code-cache=<dir>` > `VERVE_CODE_CACHE` > 默认目录；`VERVE_CODE_CACHE` 的
  `0`/`off`/`false` 表示关，空值视为未设置。
- **静默**：把「目录从哪来」做成一个枚举（`Explicit(PathBuf)` / `Default(PathBuf)` / `Off`），
  只有 `Explicit` 才 `eprintln!` 现有的 `verve: code cache … not used: {error}`（`tests/code_cache.rs` 的
  `verve_run_keeps_a_cache_with_the_flag_or_the_variable` 断言了这行）。`Default` 下 `set_code_cache_dir_with_user_secret`
  的任何 `Err`（建不了、不可写、`check_private` 不过、`HOME` 未设置、密钥不是 32 字节）都直接丢掉、继续跑，
  stderr 一个字节都不多。只读家目录、CI 容器、`HOME` 未设置都走这条路。
- 默认目录不存在时**不预先创建**：让 `set_code_cache_dir_with_user_secret` 自己建（见「给其他包的备注」第 2 条）。
- `-e`/`-p` 的源码不进缓存（现状），它 `require`/`import` 的文件照常进；`worker_threads`、`child_process`
  起的 `verve` 子进程沿用同一套判定（它们各自解析自己的命令行与环境变量，不需要新代码）。
- 关闭时既不读也不写：`--no-code-cache` 与 `VERVE_CODE_CACHE=0` 都要让 `Runtime` 拿不到缓存（`disable_code_cache` 那条路），
  而不是「有缓存但不用」。默认目录下同样如此（静默地没有缓存）。

#### 第 3 节（淘汰）设计要点

- 「最近使用」用 pack 文件的修改时间：**打开 pack 时 `touch` 一次**（`File::set_modified(now)`，一次 syscall）。
  比在索引头里记时间戳便宜，也不需要改格式（格式一改，上一版写的 pack 就全部作废）。
- 触发时机：**不在启动路径上**。放在第一次真正 flush 之后（`write(settled=true)` 返回后、且只在这一次运行里跑一次），
  即主脚本已经跑完、进程正要退出时；此时读目录、删文件都不影响首屏。
- 规则：删掉**其他构建**（文件名 `<指纹>.pack`，不等于当前构建且不是当前构建解析后的路径）里
  「超过 14 天未使用」的 pack；目录总大小超过 **512 MB** 时按最近使用从旧到新删其他构建的，直到低于上限。
  当前构建的 pack 永不删。
- 限频：目录里放一个时间戳文件（例如 `last-sweep`），一天最多查一次；`stat`/`read_dir`/`remove_file`
  的任何失败都只是跳过，不报错、不影响退出码。
- 做成可复用函数（例如 `code_cache::sweep(dir, current: &Path, now)`），P42 用它清 Electron 应用的旧 generation 目录。
  签名只吃目录与当前 pack，不碰 `Runtime`，这样两边都能调。

#### 第 4 节（并发写）设计要点

- 临时文件名已有进程号 + 8 字节随机后缀（`write_atomically`），互不覆盖；改名之前的「重新读盘 + 合并」现状已有
  （`write` 里读整份 pack、逐条验签、`PackWriter` 按 key 去重）。**竞争窗口**是「读到改名之间」：
  这期间另一个进程写进去的条目会被覆盖掉——最多丢另一个进程**一轮**的新增条目，pack 本身永远完整（改名是原子的）。
  这与任务书的说法一致，本轮实测未发现损坏（并发测试留到第二阶段）。
- **Windows 上改名撞上另一个进程正打开着目标文件**（`ERROR_ACCESS_DENIED` / 共享冲突）时：放弃本次写入，
  把待写条目留在 `pending` 里让下一次 flush 再试（或直接丢弃，等下次编译），**不重试、不阻塞、不报错**。
  今天的 `write_atomically` 已经会删掉临时文件并把错误吞掉（`let _ =`），要补的是「别把 `pending` 清空」，
  即失败时保留 `pending`、成功时才 `*state = Pack::default()`。
- 临时文件在失败时删掉（现状已有）。
- 测试：4 个进程各自加载不同模块并 flush，重复若干轮；最后 pack 可读、每条标签有效、每个进程的条目在下一轮后都在。

#### 给其他包的备注

1. **`verve run` 默认不给文件系统权限，而 `require` 把权限拒绝报成「找不到模块」。** 实测：
   `require('typescript')`（`node_modules` 里，工作目录之外）不带 `-A` 时报
   `Cannot find module 'typescript'`（`code: 'MODULE_NOT_FOUND'`）；同一目录下的 `require('./hi.cjs')` 报
   `ERR_ACCESS_DENIED` + `permission: 'FileSystemRead'`。也就是说裸说明符这一路把真正的失败原因盖住了。
   测量/测试脚本要读工作目录之外的文件必须加 `-A`；这条**值得单独开一个包修**（让 `ERR_ACCESS_DENIED` 透出来，
   而不是变成 `MODULE_NOT_FOUND`）。本包不改它。
2. **用 Git Bash 的 `mkdir` 预先建好的缓存目录会被判为 "not private to this user"**（新建目录继承了父目录的 DACL，
   而 `check_private` 只接受仅本人可达的 DACL）。让 verve 自己建目录；测试里也不要在跑之前 `mkdir` 缓存目录。
3. **P42**：淘汰函数（第 3 节）直接复用；「第二次才写」这条只属于 CLI 的默认值，嵌入方仍由自己决定
   （`Runtime::new()` 默认关不变），Electron 要不要跟着改由 P42 定。
4. **P63/P66**：暖缓存下函数首次调用是「从字节造 codeblock」，不走 AST 编译；JIT 的门槛计数不受影响（P62 已记）。
5. **P64/P65**：`CodeCacheStats` 如有新字段，记得本包会再加「标记命中/未命中」的计数。

已知问题：

- 单文件脚本即使暖缓存也不比不开缓存快（29.2 对 27.9）：它没有可省的解析，只有读 pack 与校验。
  推荐方案用「值得缓存」门槛让它任何一跑都不碰缓存；门槛以下的小脚本默认开后仍是净亏。
- 暖缓存的哈希开销随源码大小线性增长（`typescript` 暖跑里 16.98 求键 + 38.18 读回验签，整跑 229 ms），本包不动；
  见 `docs/startup.md` 的「Faster reading back」。
- 表 B 的 `write` 在组合上 4.76 ms、单文件 4.43 ms，几乎不随 402 B → 1 MB 变化：这段基本是建临时文件（带 DACL）
  与改名的固定成本，不是写字节；`typescript` 的 17.8 MB 才把它推到 9.20 ms。
- 表 C 的 I/O 数字在两次 pass 之间差 2–3 倍（负载 7.9–21.5% 对 29–48%），本包所有结论都按较差的那组给，
  不按最好的一组算。
- 首次建密钥（16.1–34.9 ms）与首次建目录（6.3–11.3 ms）在重负载下是本轮最贵的两项固定成本；
  它们决定了「第一次不建密钥」这条设计，也决定了「值得缓存」门槛必须在知道载入量之后才判定。
- 组合负载本轮的 `startup.mjs` 是自建脚本（31 个入口、脚本内 56.5 ms），不是 `docs/startup.md` 里那份原始脚本；
  两者的绝对时间不可直接对比，但冷/暖/无缓存三列的口径一致。
